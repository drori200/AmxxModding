# Independent PAWN review findings

This review maps the pinned guides to **86 topic obligations**, examines selected consequential claims and audits the preserved example results. It does **not** certify the advancement gate, every language claim, every diagnostic, or all configurations. AMXX research remains blocked until the gate's separate requirements are satisfied.

The machine-readable [coverage inventory](coverage-inventory.json) records guide sections and printed page numbers, source archive/document hashes, the case files available when reviewed, their hashes and the remaining obligations. A mapped case means that source and an oracle exist; it does not mean that the case passed. The diagnostic index is a location index with upstream expectation links, not proof that every diagnostic was triggered. These files were produced by a reviewer separate from the author of the lab harness and original test cases.

## VM width defects: independently checked mechanism and retained experiments

Stable `amx/amx.c` defines `_W` at 2078 as a write of `cell`, but `_W32` at 2081 writes `uint32_t`. The portable C interpreter uses `_W32` in five operations whose semantics require a cell-sized write:

- `OP_FILL` at 2702–2712 advances by `sizeof(cell)` while writing 32 bits per iteration. `OP_FILL_P` at 3406–3408 reaches the same implementation.
- `OP_SWAP_PRI` and `OP_SWAP_ALT` at 2768–2777 read a full cell with `_R` but write 32 bits back to the stack.
- `OP_CONST` and `OP_CONST_S` at 3150–3159 write 32 bits for a cell value.

For **16-bit cells**, these writes overlap the adjacent cell; the last fill store can also extend beyond the region validated by the opcode. For **64-bit cells**, they write only half of a cell, potentially discarding significant bits or retaining stale upper bits. On the reviewed default memory macros and **32-bit cells**, store width matches cell width. This is a source-backed defect mechanism in the portable C path, not a claim about assembler/JIT cores, custom memory access macros or all observed failures. Other `_W32` uses, such as four-byte string stores and explicit four-byte block-copy chunks, have a different purpose and must not be globally replaced.

The separately authored [defect experiment ledger](../evidence/pawn-defect-probes.json) was inspected in this review. It retains the upstream `amx.c` hash `ed90f2709ac20dbd34c40c222465fa38f6c8a09a84813b7ea50b345e2fcc7ee4`, a hash of the local five-store diagnostic repair, exact build/compile/run commands, timeouts and traces. The upstream source remains unchanged.

These tests are stronger than compilation-only evidence. However, the local experiment changes five stores together, so it does not by itself attribute each repaired trace to one individually isolated edit. The opcode paths and source analysis support the narrower mechanism above; disassembly or a one-edit comparison can further tighten per-opcode attribution. A local diagnostic repair is not an upstream release or proof that every 16/64-bit defect is fixed.

A separate documentation inconsistency affects the binary header description: Implementer p.82 describes `AMX_FLAG_NOCHECKS` as one-byte opcodes. Stable `amx/amx.h:407` instead identifies omission of array-bounds checks and `BREAK` opcodes. Bytecode inspection should use the pinned header and opcode implementation; the guide's flag sentence is not an adequate oracle.
